# Найденные проблемы

Дата ревью: 03.09.2026.

## Критические

### 1. Docker-образ не собирается из-за несовместимой версии Poetry

- `Dockerfile:9` устанавливает Poetry 1.8.3.
- `pyproject.toml` использует секцию `[project]` (PEP 621), поддержка которой появилась в Poetry 2.0.
- `poetry.lock:1` создан Poetry 2.4.1 и имеет формат lock-файла 2.1.
- Поэтому команда `poetry install` из `Dockerfile:17` несовместима с конфигурацией проекта и завершится ошибкой.

Рекомендация: использовать в Dockerfile Poetry версии не ниже той, которой создан lock-файл, либо привести `pyproject.toml` и `poetry.lock` к формату Poetry 1.8.

## Высокий приоритет

### 2. Файл с выгрузкой тикетов попадает в Docker-образ

- `Dockerfile:19` выполняет `COPY . .`.
- В `.dockerignore` отсутствует правило для корневого `tickets_export.json`.
- Файл `tickets_export.json` сейчас присутствует в рабочей папке, поэтому при локальной сборке его содержимое будет сохранено в одном из слоёв Docker-образа.

Это может привести к раскрытию описаний тикетов, переписки и другой служебной информации.

Рекомендация: добавить `tickets_export*.json` в `.dockerignore` и не хранить реальные выгрузки внутри контекста сборки.

### 3. Сохранённый XSS в HTML-отчёте

В `index.html:124-153` значения из выгрузки вставляются через `innerHTML` без экранирования:

- автор и текст комментария;
- события;
- идентификатор, название, автор и описание тикета.

Если одно из этих полей содержит HTML с обработчиком событий или тегом `script`, код может выполниться при просмотре отчёта.

Рекомендация: создавать элементы через DOM API и записывать пользовательские данные только через `textContent`. Если HTML действительно нужен, применять проверенный HTML-санитайзер.

### 4. CLI-парсер требует Telegram-токен

- `intraservice_parser.py:13` импортирует модуль `config`.
- При импорте `config.py:51` обязательным образом читает `TELEGRAM_BOT_TOKEN` и завершает процесс через `sys.exit`, если токена нет.

В результате самостоятельный CLI-запуск парсера невозможен без настройки Telegram, хотя Telegram для CLI-режима не используется.

Рекомендация: проверять Telegram-токен только при запуске `bot.py`, а общие настройки парсера отделить от настроек бота.

### 5. Ошибка конфигурации allowlist открывает бота всем пользователям

`config.py:58-61` молча отбрасывает все значения `ALLOWED_TELEGRAM_USER_IDS`, которые не прошли `isdigit()`. Если переменная заполнена с ошибкой и в результате множество остаётся пустым, `bot.py:41-44` разрешает доступ любому пользователю.

Рекомендация: валидировать каждый ID при старте и завершать запуск с понятной ошибкой. Пустой или некорректный allowlist в production должен запрещать доступ, а не разрешать его всем.

### 6. Параметры пагинации передаются в теле GET-запроса

В `intraservice_parser.py:127-136` параметры `page` и `tb_orderby` передаются через аргумент `data`:

```python
session.request("GET", url, data=data)
```

Для GET-запросов параметры обычно должны передаваться через `params`. Если Intraservice не обрабатывает тело GET, сервер будет возвращать первую страницу при каждом запросе. Проверка повторяющегося первого ID остановит экспорт, и в результат попадёт только первая страница.

Рекомендация: сверить контракт Intraservice API и, если параметры являются query-параметрами, заменить `data=data` на `params=data`.

## Средний приоритет

### 7. У сетевых запросов отсутствуют тайм-ауты

Тайм-аут не установлен в следующих местах:

- `intraservice_parser.py:33` — авторизация;
- `intraservice_parser.py:134` — загрузка страницы списка тикетов;
- `intraservice_parser.py:190` — загрузка карточки тикета.

При сетевой проблеме поток экспорта может зависнуть на неопределённое время, а Telegram-команда `/export` не завершится.

Рекомендация: задать connect/read timeout для всех запросов и обрабатывать `requests.Timeout`.

### 8. Документация не соответствует фактическому поведению

Обнаружены следующие расхождения:

- В `README.md:54-59` пример `.env` содержит только логин и пароль, хотя для запуска бота обязателен `TELEGRAM_BOT_TOKEN`.
- В `README.md:247-253` используется `Restart=unless-stopped`. Это значение относится к Docker Compose и недопустимо для systemd.
- В `README.md:95-101` утверждается, что Docker-бот сохраняет выгрузки в `./exports`, но `bot.py:127-134` создаёт JSON в памяти и только отправляет его в Telegram.
- `index.html:113` всегда загружает корневой `tickets_export.json`, а CLI сохраняет timestamp-файлы в каталоге `exports` (`intraservice_parser.py:332-336`). Новые выгрузки нельзя просмотреть описанным в README способом без ручного копирования или переименования.
- В разделе структуры проекта (`README.md:21-34`) перечислены отсутствующие `parser.py`, `task.md`, `add.md` и `test.py`; фактический парсер называется `intraservice_parser.py`.

Рекомендация: обновить примеры конфигурации и запуска, исправить systemd unit и описать единый фактический путь к файлам экспорта.

### 9. Заявленное обновление прогресса не реализовано

В `bot.py:92-99` комментарий сообщает, что статусное сообщение будет периодически обновляться. Функция `log` только добавляет строки в `progress_lines`, но этот список больше нигде не читается. Пользователь видит лишь сообщение о начале и итоговый результат.

Рекомендация: удалить неиспользуемый список и исправить комментарий либо реализовать безопасную передачу прогресса из рабочего потока в event loop Telegram-бота.

## Проверки и ограничения ревью

- `tickets_export.json` успешно разбирается как JSON.
- Встроенный JavaScript из `index.html` синтаксически корректен.
- Автоматические Python-тесты в проекте отсутствуют.
- Python-тесты, Docker-сборка и сравнение с базовой веткой не запускались: в текущем окружении отсутствуют рабочие Python, Docker и Git.
